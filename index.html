How I work

Quality is easier to trust when the route to the result is visible.

I do not want a portfolio that only says I know Jira or Playwright. I want an employer to be able to follow the testing logic: what was expected, what I tested, what failed, how I investigated it, what was retested and what was kept in regression.

My previous software-development and data experience also helps when I need to think beyond the UI - through HTTP behaviour, API responses, data validation and debugging.

02What happened when tests failed

The strongest evidence in this project is not the pass count. It is what happened after the failures appeared.

BG-27FIXED

First obstacle not visible

The initial game state failed because the first obstacle started outside the visible area. The implementation was corrected and targeted retesting passed.

View retest evidence ↗
BG-28NOT REPRODUCIBLE

Mouse-click start observation

A controlled Chromium follow-up produced 20/20 successful attempts. No BG-28-specific source change was made, so the observation was closed as Not Reproducible.

Controlled repeat test · 20/20 passed
BG-30KNOWN / DEFERRED

Frame-rate-dependent movement

Movement uses fixed values per animation frame. The limitation remains visible as technical risk rather than being hidden simply because the regression suite passes.

Future improvement: elapsed-time / delta-time movement

Regression automation

Automate stable behaviour; keep the limitations visible.

The Playwright JavaScript suite covers game state, controls, gravity, obstacles, scoring, collision, restart, browser compatibility and smaller-screen controls. Local verification finished at 24/24 Chromium regression checks plus 3/3 supported-browser compatibility checks.

CI accuracy: GitHub Actions runs a defined Chromium regression workflow plus Firefox compatibility smoke testing. I do not describe the CI run as the same 27/27 local execution.
